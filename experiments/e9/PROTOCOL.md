# E9 protocol (pre-registration)

Status: committed ALONE, before any E9 harness code and before any validation or metric run on any E9 polyline. Any later change to this
file is a deviation and must be listed in `results/NOTES.md`.

Subject: the polyline input path of TrackLab/TrackSeed (`src/polyline.ts`; CLI `validate-polyline`, `metrics-polyline`), applied to tracks
that the authors did not create. Validator and metrics are those of master `6a177ea` (validator hardening WP7a: scale-relative tolerances,
polyline duplicate removal, `--resample-smooth`, sampling guideline in `docs/validator.md`). **No validator or metric parameter is changed
in E9** (library defaults everywhere, no `--limit`, no `absoluteTolerances`); nothing is tuned, so there is no DEV/HELD-OUT split.

## 0. Disclosure: what I had seen before writing the predictions

- Phase 1 outputs only: counts of tracks and generator failures per source, points per track, median spacing, length, width, unit
  (`PHASE1_REPORT.md`, `dryrun/summary.txt`), and that every polyline file parses. No validation, no metrics, no plots, no CLI run on any polyline.
- I read the source code of the generators while writing the adapters (so I know the mechanisms: juangallostra's hull-and-displacement construction
  on an integer pixel grid with a 20 px minimum point distance and a 90 degree angle limit; AMZ's own curvature limit 1/3.75 per metre and
  its own self-crossing rejection; CarRacing's turn-rate limit of 0.31 rad per 3.5-unit step; track_gen's random turn rate 0.05-0.95 rad per
  5-unit step with half width 5).
- For the E5 generator I know the committed E5 result line for road width 4: 987 of 1000 pass (98.7 %) under the validator of that time
  (v1.1.0, `ratio` seam mode, no scale tolerance). The validator has changed since (default kink rule, hardening), so this is a prior, not a result for E9.
- To wire the E5 generator into the E9 pipeline I ran E5's own build and `run.mjs node22` into a scratch directory outside the repository and looked only at the output shape and the outcome count (all 1000 seeds have outcome `ok`, 1000 polylines). No validation or metric of them.
- I did NOT look at any real-circuit or bacinger validity, nor at any metric of any E9 track.

## 2. Preprocessing arms

For each track and width W of the run, `trackFromPolyline({points, width: W, closed: true}, options)` then `validateTrack(track)` with library defaults.
Built-in duplicate removal always applies (it is part of the path). Heights are ignored (planar x/z, y = 0).

- **raw**: no resampling (`options = {}`). The validator judges what the source emits. This is the primary arm for validity.
- **smooth**: `options = {resampleSmooth: {spacing: s}}`, s = 0.25 x W of that run, stated per source in the results (juangallostra 10 px, AMZ 0.75 m,
  CarRacing 3.333, track_gen 2.5, E5 1.0, TUMFTM 0.25 x the circuit's width, bacinger 3 m, drift-school 0.55 / 0.375 / 0.25 / 0.2 / 0.1875).
  This is a sensitivity arm that separates sampling artefacts from geometry; it changes the validated geometry and is always labelled as such.
- **norm-720** (metrics only, Q2): `options = {resampleSmooth: {spacing: S}}` with S = L / 720, L = perimeter of the raw polyline (closing edge included), so that
  every track has about 720 samples (n = round(spline length / S)). Reason: the raw sampling differs by a factor of 50 between sources (0.1 units to 38 m),
  and the curvature statistics of a 3-point estimator depend on sampling; a fixed relative sampling makes tracks comparable. 720 is the polygon size for which
  `docs/metrics.md` states the discretisation bias of the normalised curvature (1 - 3.2e-6 for a circle). This arm is NOT validated.
  Metrics on the raw arm are reported as a descriptive secondary table.

A build error (RangeError from `trackFromPolyline`) or a validator exception is recorded as outcome `error` and counts as not ok.

## 3. Research questions, measures, decision rules

**Q1 validity per source.** `ok` = `validateTrack(...).ok` (no error-severity violation; warnings are listed separately and do not fail a track).
Per source and arm: n, number ok, ok rate with Wilson 95 % interval (one track per seed, no seed clustering; for the 25 circuits every circuit is also listed
with its verdict and error codes). Two denominators: tracks produced (primary) and seeds attempted (a generation failure counts as not ok; the second rate is
given for transparency). Error-code distribution: for each error code the number of tracks that have it (a track can have several). Sampling share: the 2 x 2
table raw x smooth (ok/ok, fail -> ok, ok -> fail, fail/fail); "explained by sampling" = fail -> ok / raw failures (reported only if raw failures >= 5, else the
counts); the error codes that persist in fail/fail tracks. TUMFTM sensitivity: the same on the minimum width (smooth spacing 0.25 x minimum width).

**Q2 geometric/expressive range.** Scale-normalised fields of `computeMetrics` on the norm-720 arm: `meanAbsCurvatureNorm`, `p95AbsCurvatureNorm`, `maxAbsCurvatureNorm`,
`curvatureEntropyBitsNorm`, `straightLengthFractionNorm`, `turnCountNorm` (6 metrics; legacy unit-bound fields are not used). Descriptive: min, quartiles, max per source.
Distance per metric between a source and the TUMFTM circuits: d = W1 / sd_real, where W1 is the 1-D Wasserstein (earth mover's) distance between the two empirical
distributions (exact, via the quantile functions) and sd_real is the sample standard deviation (n - 1) of the metric over the 25 circuits. A source "differs" from the real
circuits in a metric iff d > max(0.5, p95 of d over 2000 random 12/13 splits of the 25 circuits into two groups, split RNG mulberry32 seed 20261113). The 0.5 is the
conventional "medium effect" magnitude and the split baseline keeps the rule above the noise of a 25-circuit reference; both are fixed here, from the real data alone.
No significance test is made; the numbers are descriptive. Family-level d (CAR pooled) is computed the same way. bacinger is compared with TUMFTM the same way as a
real-vs-real reference (supplementary).

**Q3 cost.** Wall time per track of `trackFromPolyline` + `validateTrack` + `computeMetrics` on the raw arm (one pass per track after the correctness pass, `performance.now()`),
reported as median, p95, max per source with the machine (CPU model, cores, Node version). Indicative only; timings are written to a separate file that is excluded from the
determinism hash.

**Q4 harness determinism.** The whole E9 analysis (`run.mjs` then `analyze.mjs`) is run twice into separate scratch directories; the sha256 of every output file except
`timing.json` must be identical (written to `DETERMINISM.txt`). The polyline extraction was already shown byte-identical across three runs in phase 1; it is re-checked by
the hash of `build/polylines/SHA256SUMS`.

## 4. Predictions (numeric, written before any run; failed ones are reported as failed)

Thresholds are stated with the reason. All refer to the pre-specified measures above.

Q1 (validity, raw arm unless stated; rates are over tracks produced)
- P1.1 TUMFTM circuits: raw ok >= 80 % (>= 20 of 25). Reason: 5 m spacing on smoothed centre lines, authors' widths; the chosen median width is moderate.
- P1.2 TUMFTM: smooth ok >= raw ok - 1 circuit (smoothing does not make real circuits worse by more than one).
- P1.3 TUMFTM sensitivity: raw ok at the minimum width >= raw ok at the median width, and the difference is <= 3 circuits.
- P1.4 bacinger (supplementary): raw ok <= 50 %, smooth ok >= 70 %. Reason: 12-38 m spacing makes every corner entry a single sharp vertex (turn > 12 degrees against straight neighbours, i.e. `LOCAL_KINK`),
  which `--resample-smooth` is designed to remove (docs/validator.md rounded-rectangle probe).
- P1.5 AMZ: raw ok >= 90 %. Reason: its own curvature limit (R >= 3.75 for half width 1.5) and its own buffer self-crossing rejection, 0.3 m spacing on a spline.
- P1.6 E5 generator at W = 4: raw ok >= 90 %. Reason: the E5 prior (98.7 % under the older validator) with allowance for the stricter kink rule.
- P1.7 juangallostra: raw ok <= 40 %; the most frequent error code is an edge/centreline self-intersection or fold code (`SELF_INTERSECTION_EDGE`, `EDGE_EDGE_INTERSECTION`, `EDGE_FOLD`,
  `SELF_INTERSECTION_CENTERLINE`), not `LOCAL_KINK`; smoothing rescues <= 30 % of its raw failures. Reason: points >= 20 px apart with turns up to 90 degrees give radii of 10-15 px against a 20 px half width.
- P1.8 CarRacing: raw ok between 50 % and 90 %.
- P1.9 track_gen: raw ok < raw ok of CarRacing, and <= 60 %. Reason: same construction with a larger step relative to its half width and a random turn rate up to 0.95 rad.
  Consequence if true: the two members of one family differ by > 10 percentage points, so "family" results are not interchangeable with source results.
- P1.10 For every source (primary and supplementary, every drift-school stage) the share of tracks that are ok under raw but not ok under smooth is < 2 %.
- P1.11 Generation failures: reported counts are exactly the phase-1 counts (AMZ 79, juangallostra 2, others 0, E5 0); a deviation is a harness fault.

Q2 (range; "differs" as defined in section 3)
- P2.1 Each of the five primary generator sources (juangallostra, AMZ, CarRacing, track_gen, E5) differs from the TUMFTM circuits in at least 2 of the 6 normalised metrics.
- P2.2 Every one of those five sources has a median `straightLengthFractionNorm` below the median of the real circuits.
- P2.3 The E5 generator has the smallest mean d over the 6 metrics of the five sources.
- P2.4 bacinger vs TUMFTM (real vs real, supplementary): it differs in at most 1 of the 6 metrics.

Q3 (cost, raw arm, this machine)
- P3.1 median time per track < 20 ms for every generator source and < 50 ms for TUMFTM; p95 < 100 ms for every primary source; no track above 1 s.

Q4
- P4.1 the two analysis runs give identical hashes for all non-timing outputs.

Reporting rule: each prediction is listed with the observed value and the verdict (held / failed / not testable, with the reason). The summary states how many held.

## 5. Procedure (fixed order)

1. This file is committed alone.
2. Harness committed before any run: `run.mjs` (all arms, writes `tracks.csv` and `timing.json`), `analyze.mjs` (writes `SUMMARY.json`, `SUMMARY.md`), `make-figure.py`, `run-all.sh`,
   the E5-generator adapter, and the small adapter change that stores the per-point width range of TUMFTM circuits in the polyline file (`meta`). The phase-1 extraction is re-run
   in that commit and its logs refreshed (before any validation).
3. Run `run-all.sh` (network needed for the pinned fetches). Results: `results/SUMMARY.md`, `SUMMARY.json`, compact per-track `tracks.csv.gz`, `timing.json`, one combined figure
   (validity bars per source, raw vs smooth, with Wilson intervals; small multiples of three normalised metrics: `meanAbsCurvatureNorm`, `straightLengthFractionNorm`, `turnCountNorm`,
   real circuits highlighted; PNG + SVG), `NOTES.md` (deviations), `DETERMINISM.txt`. `npm test` once at the end.
4. Row E9 in `REPRODUCE.md` and a group `e9` in `scripts/reproduce-check.sh`.

## 6. Limits stated in advance

- Real-circuit data come from OpenStreetMap-derived, smoothed, hand-measured files: validity statements concern the files. bacinger's width is assumed.
- One track per seed; generators are run with their default parameters only (AMZ: one mode, CarRacing: its fixed constants); results do not describe their parameter spaces.
- Widths of generators are their declared constants; width-dependent checks follow from those choices. Only TUMFTM has a width sensitivity run.
- The smooth arm and the norm-720 arm change geometry; neither can repair a corner the input does not contain.
- Wasserstein distances compare 1000-track samples with a 25-circuit reference; the split baseline is the only allowance for that noise.
- Timing is one machine, one process, indicative.
